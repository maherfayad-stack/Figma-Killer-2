# Plan: Figma-style multiplayer on a Studio board
> **Purpose:** the design for Figma-style multiplayer on a Studio board (bundles MP-1..MP-8, decisions OD-MP-1..11) · **Read when:** before starting or reviewing a bundle of this plan · **Trust:** live design, not built (2026-10-10; STATE.md says which bundles are in flight) · **Owner:** studio-architect; studio-scribe folds shipped bundles out · **Verified:** 2026-10-10 (design read against the code, nothing run)

Not on ROADMAP.md; proposes a new program "MP". Grounded in: projectWriteLock.ts (FIFO, per real path, AsyncLocalStorage reentrant, write sessions), projectWatch.ts + projectChangeFeed.ts (origin `studio` vs `outside`, seq journal), undoJournal.ts (whole-file SHA CAS, `restore-stale`), sourceIdentity.ts + `expect` fingerprints (`element-moved` refusal, P1-A), structuralCommitQueue/structuralWriteRetry, editorBridge.ts (`site:${projectKey}`, per-user), routeGate/routeCapabilities, boardsApi (whole-file POST), liveOrigin.ts (the only existing Bun websocket handler; the admin listener has none).

GOAL: several people (and the MCP agent) see each other live on one project's board and edit it concurrently, with no lost write, honest refusals, and per-user undo.
DONE WHEN: two real browsers + one MCP connector on one project: avatars/cursors/selections visible, edits by one appear on the others within ~300 ms, two simultaneous edits to different props of one node both land, a true conflict refuses with "<name> changed this" and auto-retries once, each user's Cmd+Z undoes only their own last write, boards.json/notes/comments never overwrite each other. E2E two-context spec asserts all of it.

## 1. Core decision: server-ordered operations over the AST, not CRDT

Yjs over a projection rejected:
- Disk is truth and is edited outside Studio (VS Code, git pull, agent Edit tool). A Y.Doc must be diffed back against every outside change; the doc becomes a second source of truth, which violates "one honest write target".
- Text-level Y.Text merges char-by-char and can interleave into invalid JSX; the product's promise is that every write is a precise ts-morph codemod that refuses when ambiguous. A CRDT converges but never refuses; "refuse-and-say-why" is the product.
- A tree projection (Y.Map per node) needs a lossless bidirectional AST<->Y mapping incl. formatting, comments, `.map` rows, props-vs-class-vs-css-file routing. That is the parser/codemod stack rewritten.
- CRDT's win (offline, peer-to-peer, no central order) is unused: Studio is already a single authoritative server with a write lock. Self-hosted single process is the stated deployment.
Server-ordered ops win because the ordering mechanism already exists (the lock) and the guard already exists (`expect` fingerprints). Conflict semantic = what codemods already do: property-granular last-writer-wins; structural conflicts refuse.

Hard assumption (state in docs): one server process per project directory (in-memory lock). Multi-instance/HA is out of scope and a startup warning if two are detected is not needed.

## 2. Architecture

- Writes stay on the existing HTTP routes (`/save`, `/restore`, structural, boards, comments). They keep routeGate (404 undeclared, Origin check, capability) and the write lock. NO edit travels over the socket. This is the key simplification: the socket is a notification + presence bus only, so there is no second write policy.
- Live channel: one WebSocket per (user tab, project) at `GET /admin/api/studio/live?dir=` (Bun.serve `websocket` handler added to the admin listener). WebSocket over SSE because cursors need 20-30 Hz upstream; SSE+POST would make each cursor an HTTP request through the gate. Fallback: none (no dual path); if the socket is down the editor works single-player as today and shows a "reconnecting" chip. The upgrade is a GET so routeGate's state-changing Origin rule does not cover it: the upgrade handler must check Origin itself (CSWSH) and declare the path in routeCapabilities (`read: 'site.read'`). Per-message authority is re-derived from the session, never from a client-supplied role.
- Project room: in-memory `ProjectRoom` per real project path (same realpath keying as the lock): members, last presence per member, `epoch` (random per server start) and `rev` (monotonic int). Nothing persisted. Bump `rev` inside the write lock release path (`withProjectWriteLock` completion hook) so rev order == lock order == disk order.
- Edit fan-out: after a write session ends the room broadcasts `edit-applied {rev, actor, files[], kind}`. Reuse projectWatch classification: `studio` origin changes the room already knows via the hook; `outside` changes (VS Code, git pull) come via subscribeProjectChanges and broadcast as `outside-changed {files}` (replaces ad-hoc outsideEditReload fan-out for the board; delete the per-bridge-only path if it ends up duplicated).
- Client reconcile (the heart): each client holds `lastSeenRev`. On `edit-applied` from another actor: if no local pending/in-flight write touches those files, run the existing targeted resync (`studioBoardResync`, `/load` memoised by projectChangeFeed) and re-record identities (`sourceIdentity` replace-records path). If a local write on those files is queued/in flight, let `structuralCommitQueue` drain first, then resync once. Optimistic local overlay (unacked value edits) is re-applied over the fresh parse until its save response lands. Local write responses return `{rev, identities}`; ack removes the overlay entry. Server order always wins; clients never merge text.
- Conflicts (no new machinery beyond ordering):
  - different props / different nodes / different files: both land (codemods are property-targeted; fingerprint of the node changes with the other user's prop write -> see below).
  - Fingerprint caveat: today a value write mutates the node's fingerprint, so user B's next write with a stale `expect` would be refused by user A's harmless prop write. Fix: split `expect` into identity fingerprint (element kind + structural position, stable across prop edits) and content fingerprint (only checked when the write depends on current value, e.g. text replace). This is a parser/codemod change (MP-3a) and is the largest correctness item.
  - same prop of same node: last writer wins (server order); the loser's client sees the resync value change and an `info` toast chip "Alex changed width" only if its own write was acked first and then overwritten within 2 s. No red toast.
  - structural vs anything on the same element (move/delete/wrap while another edits it): `element-moved` or node-gone refusal -> `structuralWriteRetry` re-resolves by fingerprint once after resync; second failure is a `warning` "Alex deleted this" with the one-click remedy (undo-your-own is unavailable; offer "Reload").
  - Rejected: operation rebasing/transformation on node ids (OT). Node ids are `rel:line:col`; any structural op renumbers the file, so rebase = reparse + fingerprint relocation, which is precisely refuse-and-refresh with relocation. Do relocation server-side only for the structural queue case (already client-side in relocateCapturedIds).
- Soft locks (UX, not correctness): a peer's selection / active text edit shows a ring + name; typing into a text node another user is editing shows "Alex is editing" and defers focus. Advisory only.
- Per-user undo:
  - Client history stacks are already local per tab -> value/inverse-edit undo is per user for free; each inverse edit is a normal write with `expect`, so it refuses honestly if someone changed that prop since ("Alex changed this since, nothing undone").
  - Server `restore-journal` is the problem: CAS on whole-file SHA (`afterSha256`) means ANY peer write to the same file makes every other user's undo `restore-stale`. Replace with hunk-level journal: entry = `{actorId, files:[{rel, hunks:[{beforeText, afterText, anchorContextBefore/After}]}]}` computed by diffing before/after bytes; restore locates `afterText` by context in current bytes (exact unique match required), swaps back, else `restore-stale` naming the hunk's element. Token stays opaque; entries tagged with actor; prune per project unchanged. Delete the whole-file SHA CAS (no dual path).
  - Redo re-posts forward edit as today. Cross-user undo is never offered.
- Agent: MCP writes already take the lock and become `actor = agent:<connectorId>` (user = connector owner) -> broadcast like any edit, presence shows an agent avatar with the node/file the current tool call targets (from agentWriteSupport / editTools metadata), agentCheckpoints unchanged. Agent edits get the same `expect` refusals; an agent write that hits a human's fresh edit is refused, the agent re-reads (already its contract).
- git verbs hold the lock for seconds: room broadcasts `project-busy {reason}` / `project-idle`, UI shows a chip; saves queue (waitMs undefined) as today.

## 3. Presence protocol

Ephemeral, per room, never written to disk, 5 s TTL if no frames (heartbeat 2 s). Cursor frames throttled client 30 Hz, server coalesces to latest per member per 33 ms tick (drop-latest, no queue growth), delta-free. Coordinates in board world space (frames live on an infinite board) plus optional `frameId`-relative for scroll-in-frame; peers draw in their own viewport transform. Selection = node id list + the sender's `rev`; receiver ignores selections whose rev < its rev until its resync lands (avoids drawing on drifted line:col). Identity colour: assigned by server from `--accent-1..10` by join order, stable per user per room. Follow mode is purely client: follower subscribes to the target's `viewport` frames (sent at 10 Hz only while at least one follower exists, server tells the target `followed-by-count`); any manual pan/zoom by the follower exits follow. Cursor chat, reactions: out of v1.

TypeBox outline (`src/core/studio-live/` barrel `@core/studio-live`, shared client/server, `Type.Union` on `t`):
- C->S: `hello {t:'hello', epoch?, lastRev?, client:{tabId, name, color?}}`; `presence {t:'presence', cursor?:{x,y,frameId?}, selection?:{ids:string[], rev}, viewport?:{x,y,zoom,w,h}, activePage?:string, editing?:{nodeId}|null}` (all fields optional = partial update); `follow {t:'follow', userId|null}`; `ping`.
- S->C: `welcome {t:'welcome', epoch, rev, you:{memberId,color}, members:Member[], busy?:string}`; `member-joined|member-left {member}`; `presence-batch {t:'presence-batch', frames:[{m, cursor?, selection?, viewport?, activePage?, editing?}]}`; `edit-applied {t:'edit-applied', rev, actor:{memberId,kind:'user'|'agent'|'system', name}, files:string[], kind:'value'|'structural'|'undo'|'file-op'|'git'}`; `outside-changed {rev, files}`; `boards-changed {rev, version}`; `comments-changed {rev, threadIds?}`; `project-busy|project-idle`; `resync {t:'resync', reason}` (epoch mismatch / rev gap / overflow -> client does full /load); `error {code}`.
- Member = `{memberId, userId, name, avatarUrl?, color, kind:'user'|'agent'|'guest', role, joinedAt}`.
- HTTP additions: save/restore/structural responses gain `rev` and `actor`; request bodies gain optional `baseRev` (diagnostics only; ordering is the lock, not baseRev). Validation via TypeBox on every inbound frame; size cap 4 KB per frame; per-socket rate limit (presence 40/s, other 5/s) -> close 1008.

## 4. Permissions per role
Join: `site.read` (viewer and up). Send presence: viewer yes (cursor/selection/viewport), because Figma viewers show cursors; `editing` field ignored unless `studio.write`. Writes: unchanged, still `studio.write` through routeGate. `studio.run.project`-class events (installs, dev server) broadcast only a `project-busy`. Follow: anyone can follow anyone in the room. Agent member shown to all, disconnectable only by its owner or admin (revoke connector token = member leaves). Share-link guests (shareLinks.ts): join as `kind:'guest'`, display "Guest", presence allowed only if the share carries comment/view-live permission (see OD-MP-3); no identity beyond share id. Every socket message authorised against the session captured at upgrade AND re-checked on role change (user demoted/session revoked -> server closes rooms for that user; hook into the auth session-invalidated path).
New capability needed? No; `site.read` for join, `studio.write` for writes. Add `studio.live` ONLY if owner wants presence separately switchable (OD-MP-3).

## 5. Boards, notes, comments
- boards.json today = whole-file POST from each client -> concurrent users clobber each other (frame moves, notes). Replace with op endpoint `POST /boards/ops` taking `ops:[{op:'frame-move'|'frame-add'|'frame-remove'|'note-upsert'|'note-remove'|'section-upsert', id, ...fields, baseVersion?}]` applied under the project write lock to the freshly read file, per-field LWW keyed by entity id (add/remove idempotent; remove wins over later update; moving a frame whose page was deleted drops the op), returns `{version, boards}`; broadcast `boards-changed`. Delete the whole-file save (`saveBoards`) and its route method; GET stays. Drag gestures send ops on pointer-up, not per move; live drag of a peer's frame shows via presence `dragging:{frameId,x,y}` field (cosmetic; the commit is the op).
- Comments (commentsApi / @core/studio-comments, anchors via @core/studio-anchor): thread/reply append is naturally mergeable; make create/reply/resolve server-id-addressed ops (verify current store: if whole-file, same op treatment). Broadcast `comments-changed`. Comment pins re-resolve via `studio-anchor/resolve.ts` after each remote edit-applied resync (no new logic). Presence adds `commenting:{x,y}` composer indicator (optional).
- Sidecars under `.studio/` (frame-defaults, framework, canvas layer modules): go through the same lock; broadcast `edit-applied kind:'file-op'`; last-writer-wins on file content with `outside-changed` semantics for `.studio/canvas/`.

## 7. Risks
- Fingerprint churn makes concurrent edits refuse constantly -> MP-3a first, with a test that two users dragging different props of one node never refuse.
- Resync storms (every peer edit triggers /load) -> coalesce `edit-applied` per file over 100 ms, targeted resync only for open pages/frames, projectChangeFeed memo already bounds cost; budget test.
- Cursor load on the single Bun event loop -> server coalescing, cap members, presence not logged, drop-latest.
- Hunk undo matches wrong text -> require unique context match, else refuse; never best-effort.
- Rev/epoch loss on restart -> `resync` on epoch change; no persistence needed.
- WS auth drift / CSWSH -> upgrade-time Origin+session check, periodic session revalidation, close on demotion; security-guard reviews MP-1, MP-5, MP-8.
- Windows `fs.watch` unreliability already documented -> fan-out for Studio's own writes comes from the lock hook, not the watcher; watcher only for outside edits.
- Single-process assumption -> documented; no multi-instance.
- Dev-server HMR websocket (liveOrigin) confusion -> separate path and handler; arch gate.

## 8. Owner decisions (recommendation)
- OD-MP-1 CRDT vs server-ordered ops: server-ordered ops, refuse on structural conflict. (rec)
- OD-MP-2 Transport: one WebSocket for presence+notifications, writes stay HTTP. (rec) Alternative SSE+POST rejected for cursor rate.
- OD-MP-3 Presence for viewers and share-link guests: viewers yes; guests only on comment-capable shares, anonymous "Guest N"; separate `studio.live` capability: no, reuse `site.read`. (rec)
- OD-MP-4 Same-prop conflict: silent last-writer-wins plus an info chip, not a blocking prompt. (rec)
- OD-MP-5 Undo scope: per-user, hunk-level, never undo a peer's change; refuse with a name when a peer touched the region. (rec) vs shared linear undo (rejected: surprising).
- OD-MP-6 Soft locks: advisory rings only, no hard element locks in v1; the existing `locked` node flag is unrelated. (rec)
- OD-MP-7 Agent visibility: show the agent as a named member with its current target, visible to everyone in the room. (rec)
- OD-MP-8 Git verbs while others edit: allowed, busy chip, saves queue behind the lock (today's behaviour). (rec)
- OD-MP-9 Max room size 12, soft warn at 8. (rec)
- OD-MP-10 Deployment: single instance per project; HA deferred. (rec)
- OD-MP-11 Phasing: ship presence (MP-1/2) as its own release before touching the write path. (rec)
