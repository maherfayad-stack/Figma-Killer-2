# Path index — where everything lives

Written for agents. Look here **before** grepping the repo.

Legend: 🟢 Studio (active work) · 🟡 shared infrastructure Studio depends on ·
🔴 **read its feature doc and its own module doc before you touch it** — these
are the security- or correctness-critical files (the git and CLI spawn guards,
the path judges, the structural-edit gates, the codemods that rewrite a user's
source) where a plausible-looking change is how a real bug ships ·
⚪ dormant CMS — do not build on it, do not delete it.

## Studio: server side

Reached by `POST /admin/api/studio/delete`, the one studio route that checks a capability (`studio.write`). |

| 🟢 `server/handlers/studio/pageDelete.ts` | `deleteStudioPage(dir, pageId)` — `DELETE /admin/api/studio/page`. | 🟢 `server/handlers/studio/boardFrames.ts` | Every server-side write to `.studio/boards.json`: `autoPlaceBoardFrame`, `removeBoardFramesForPage` (its mirror, used by page deletion), `syncBoardFramesFromDisk` (the additive reconcile `studio_screenshot`/`studio_compare` run before capturing). `syncStoryBoardFrames` (W5-3) places Storybook frames on their OWN `Stories` board, ONE time each (ledger in `.studio/meta.json`'s `stories.placedPageIds`) — never a reconcile, so a deleted frame stays deleted. Written out by name so adding a registry tool does not silently widen the agent's surface. |
| 🟢 `server/ai/drivers/claudeCliWarmSession.ts` | ONE long-lived `claude` subprocess serving many turns of one conversation. It does NOT own which conversation gets which process — that is `claudeCliSessionPool.ts`, a different reason to change. `runTurn` yields the exact event type the cold path yields, so the consuming loop is identical. **The cold path (`claudeCliSpawn.ts`) remains as crash recovery, not as a legacy shim**: a dead process throws `ClaudeCliWarmSessionDeadError` and the turn silently re-runs cold. |

## Not ours (dormant CMS)

⚪ `server/handlers/cms/` · `server/repositories/` · `server/db/` ·
`server/publish/` · `server/plugins/` · `src/core/plugin-sdk/` ·

`src/admin/pages/users/`

**Three corrections this list used to get wrong** — see
[`STUDIO-CMS-REMOVAL-PLAN.md`](../../STUDIO-CMS-REMOVAL-PLAN.md)'s Traps section:

- 🟡 **`src/core/publisher/` is load-bearing, not dormant.** It is the single
  class-CSS emission engine shared by publish and canvas: `ClassStyleInjector`
  imports `PUBLISHER_RESET_CSS`/`collectBackgroundImagePaths`, the AI executor
  imports `renderNode`, and the base image/video modules import from it.
  `server/publish/**` is the removable half. Do not conflate them.
- 🟢 **`src/admin/pages/dashboard/` is Studio's own launcher** ("Overview") —
  the project grid plus both import CTAs, the first screen a user sees. Not a
  CMS widget grid. One tile is `ProjectCard.tsx` (badges + "Edited 2 days ago"
  + the Open / Rename / Duplicate / Delete `ContextMenu`, reachable from its ⋯
  button or a right-click); `DashboardPage.tsx` owns only the server calls
  behind those verbs, and every one of them redraws through
  `useStudioProjects`'s `refresh()`. The same projects are reachable from ⌘K
  via `src/admin/spotlight/providers/projectsProvider.ts`.
- `src/admin/pages/{content,data,media}/` do not exist on disk. The standalone
  Content / Data / Media / Users **workspace routes were deleted**;
  `src/admin/router.tsx` serves only `/admin/dashboard`, `/admin/site`,
  `/admin/account` and `/admin/plugins/:pluginId/:pageId`, and anything else
  redirects to the dashboard. Plugins, Users and AI management moved into the
  Settings modal (`src/admin/modals/Settings/sections/`). The
  `data_tables`/`data_rows` model underneath still powers loops, data pickers
  and publish — there is just no workspace UI for it.

Touch only when a Studio change genuinely requires it, and say so in the handoff.
